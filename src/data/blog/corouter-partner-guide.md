## 介绍

[ai.corouter.cc](https://ai.corouter.cc/) 是一个专注于 ChatGPT 等 AI 订阅代充值服务的网站。普通用户拿到卡密后，进入公开充值页面并填写必要信息，即可完成卡密校验和充值；如果只是想确认某个账号的订阅状态，也可以在首页切换到"订阅检测"标签，无需卡密、无需注册即可免费查询。

对于合伙人来说，平台提供了一套独立的业务后台。你可以在后台管理支付卡和账单信息、生成并分发卡密、查看充值记录与积分流水，也可以通过 API（或直接把接口文档交给 AI Agent）把充值能力接入自己的销售网站。换句话说，合伙人主要负责支付资源、销售渠道和客户沟通，平台则负责卡密校验、账号预检、充值工作流、订单状态及积分结算。

平台近期做了一次比较大的架构调整：**卡密池和卡片池是两套独立的资源**。卡密只在生成时固定支付地区、最终套餐和积分成本，并不提前绑定任何一张卡；真正的银行卡只在订单执行时才按套餐规则被临时领取，直到订单成功或进入不可逆结果后才与卡密永久绑定。这个变化会体现在下面注册、生成卡密和 API 的多个环节里。

完整的业务流程可以概括为：

1. 在邀请码小店自助购买一枚邀请码并注册合伙人账号（注册即赠 50 业务积分）；
2. 确认可用积分，添加支付卡并按最终套餐放入对应卡池；
3. 向独立卡密池按地区和套餐生成卡密（此时尚未绑定任何卡片）；
4. 将卡密出售或分发给客户；
5. 客户在公开页面自助完成账号检测与充值提交，订单执行时才会领取具体卡片；
6. 在后台跟踪卡密池、卡片池、订单状态和积分流水——异常订单由系统自动判定终态，不再需要人工复核。

如果想先了解官方说明，也可以查看[合伙人机制与参与指南](https://ai.corouter.cc/partner-guide)。

## 注册与申请

合伙人注册目前以**自助购买邀请码**为主：前往[邀请码小店](https://shop.corouter.cc/products/ai-corouter-partner-invite)购买 1 枚一次性邀请码，付款后系统自动发货，在订单详情复制完整邀请码即可注册。每枚邀请码仅可成功注册一次，使用后立即失效，请妥善保管并在有效期内完成注册。

打开注册页后依次填写邀请码、合伙人名称、登录用户名、密码和确认密码：

- 合伙人名称至少 2 个字符；
- 登录用户名至少 3 个字符且不包含 `@`，并且全平台唯一（提示已占用时请更换用户名）；
- 密码为 8–72 个字符，需要两次输入一致。

注册成功后会自动进入控制台概览，并**获赠 50 个业务积分**——足够覆盖 5 次 Go/Plus 套餐代付，或 2 次 Pro 5x/Pro 20x 套餐代付后还剩 10 积分，方便先完整走通一次流程再决定是否继续。

如果购买、自动发货、邀请码状态或订阅操作遇到问题，仍然可以联系平台负责人：

注册成功后，每位合伙人都有独立的数据范围，只能访问自己名下的支付卡、卡密、订单、积分和 API Token，不会看到其他合伙人的业务数据。登录密码和 API Token 都应妥善保管，Token 只放在自己的服务端，不要写进前端代码、公开仓库或请求日志。

## 开始前需要准备什么

正式生成卡密之前，建议按顺序确认积分、支付地区和支付卡这三项内容。

### 1. 确认可用积分

积分是平台内部的业务结算单位，充值比例为 **1 元人民币兑换 10 积分**，1 元起充、单次最高 100 元，通过支付宝完成付款。注册赠送的 50 积分会直接计入余额。订单提交后，系统会先按套餐预扣积分，等支付结果明确后再完成结算，因此后台显示的账户余额和可用积分可能暂时不同：

> 可用积分 = 账户余额 - 预扣积分

建议在开始分发卡密前预留足够积分，并定期检查积分流水。如果可用积分不足，新订单可能无法继续处理。

### 2. 选择支付地区和套餐

生成卡密前，可以调用 `GET /payment-regions` 查看当前启用的支付地区（目前内置支持 **PH、US**，实际范围以接口返回值为准），再用 `GET /plan-offerings?region_code=PH` 之类的请求查看该地区当前启用的套餐、小计、税费、总价和积分成本。选错地区可能导致支付卡与账单地区不匹配，付款失败。

### 3. 添加支付卡并配置卡池

在合伙人后台添加用于代充的海外信用卡，卡号需为 12–19 位数字，仅限**境外发行**的 VISA 和 MasterCard（不要添加中国大陆发行的卡片），并准确填写持卡人姓名、有效期、CVV 以及账单地址。如果暂时没有合适的卡片，可以通过 [OnePay 虚拟信用卡](https://cutt.ly/IyrMR4Mg) 自助开卡，开卡费约 2U，适合首次小量尝试；菲律宾地区的 GPT 订阅建议选择卡头 `441357`。填写账单地址时可以使用平台的"一键生成免税州地址"功能，自动填入 Delaware、Oregon、Montana、New Hampshire、Alaska 等美国免税州地址，免除销售税、降低代充成本。

添加卡片时需要选择所属**卡池**：`all`（全套餐卡池，省略时的默认值）、`go`、`plus`、`pro_5x`、`pro_20x`。专属卡池只承接对应的最终套餐，全套餐卡池作为公共后备；派单顺序固定为"同套餐专属卡池优先，全套餐卡池兜底"。每张卡片会记录**绑卡暴露次数**（只统计首次向远端提交绑卡的订单数，5 次是选卡参考值，超过仍可继续使用，不设硬上限），以及是否处于**冷却期**——可归因于卡片的失败会让卡片进入冷却，冷却期内的卡片不参与派单；管理员解除冷却不扣积分，合伙人自己解除则固定扣除 **10 积分**（`paused` 人工暂停和冷却是两种独立状态，互不转换，且只有 active、未过期的卡片才能解除冷却）。

支付卡由合伙人自行维护，建议先生成少量卡密完整跑通一次流程，确认卡片、地区和账单信息都能正常工作，再扩大分发规模。

## 卡密池与卡片池：两套独立的资源

这是本次更新里最核心的架构变化，建议先理解清楚再开始批量生成卡密：

- **卡密池**保存待交付的套餐凭证。卡密生成时就固定了支付地区、最终套餐、币种、金额和积分成本（价格快照），但**不会**提前占用或绑定任何一张卡片，生成阶段也不消耗卡片的绑卡暴露次数。
- **卡片池**保存真正用于付款的银行卡资源。具体使用哪张卡，只在客户提交充值、订单进入执行阶段时才按卡池规则临时领取。
- 只有当订单成功，或者付款进入"不可逆结果"边界（比如已经提交付款且无法确认是否扣款）之后，卡密才会与实际使用的那张卡**永久绑定**；在此之前卡密的绑定状态始终是"未绑定"，可以随时停用、销毁换新，不影响卡片池。
- 归档一张卡片只会让它退出后续派单，不会隐藏或停用任何已经生成的卡密；卡密池和历史核销记录始终保留。

简单说：卡密决定"卖的是哪个套餐、多少钱、扣多少积分"，卡片池决定"钱从哪张卡出"，两者在执行订单之前互不影响。

## 生成和分发卡密

准备好积分与支付卡后，就可以在后台按地区和套餐向卡密池生成卡密（单次可生成 1–50 枚）。卡密可以直接发送给客户，也可以录入自己的订单系统，由自己的销售渠道完成展示和交付。交付前建议确认：对应专属卡池或全套餐卡池至少有一张可用卡片，且可用积分足以覆盖卡密显示的积分成本。

卡密有以下几种状态：`unused`（未使用）、`processing`（处理中）、`used`（已使用）、`disabled`（已停用）、`expired`（已过期）、`destroyed`（已销毁）。只有 `unused` 状态的卡密可以手动停用；已停用的卡密可以恢复，也可以批量销毁换新——原子销毁一批未使用或人工停用的卡密后，会按各自原套餐和价格快照生成一一对应、重新计算有效期的新卡密（常用于分发批次泄露或分发错误的场景），旧卡密之后只返回打码值。

客户拿到卡密后的操作很简单：

1. 打开 [ai.corouter.cc](https://ai.corouter.cc/)；
2. 输入卡密并完成校验；
3. 登录 ChatGPT，粘贴完整 Session 数据，系统自动检查账号状态并继续充值；
4. 提交后等待系统处理，页面会展示三步流程的实时进度，并可查看最终结果。

客户不需要注册合伙人后台账号。合伙人则可以在控制台查看自己名下的充值记录、处理状态和积分变化。为了方便售后，建议在发放卡密时同步记录自己的订单号、客户联系方式、卡密和发放时间，但不要在公开群聊中直接展示完整卡密。

## 账号充值条件与订阅状态检测

平台提供了一项独立的免费功能——**订阅状态检测**：无需卡密、无需注册，在首页切换到"订阅检测"标签，粘贴 Session JSON、Bearer Token 或裸 Access Token，就能查到目标账号当前的套餐、订阅状态、自动续费、到期时间、账单币种与地区、账户类型和欠费状态等信息。建议在正式充值前先用这个功能确认账号是否符合条件。

只有同时满足以下条件的账号，充值提交才会被放行：

- 远端明确判定为 **Free** 套餐（Go、Plus、Pro 等任何非 Free 状态都会被拦截，直到订阅明确更新为 Free）；
- 是 **Personal 个人账户**，而不是团队/企业工作区；
- 账号历史账单币种与本次卡密订单币种兼容。

以下情况会导致系统直接停止提交，需要先处理再重新检测：

- 账号已有生效中的订阅（包括已关闭自动续费但未到期、仍在宽限期或赠送的有效订阅）——需要等当前订阅到期、检测结果显示 Free 后才能继续；关闭自动续费只在下个计费周期生效，当前周期内仍算"有效订阅"；
- 当前选择的 ChatGPT 工作区不是 Personal 个人账户；
- 认证信息过期或缺少账号上下文，需要重新获取 Session 后再检测。

如果在付款环节前就命中以上任意一种情况，系统会停止提交，卡密恢复为未使用、套餐预扣积分完整释放，可以更换符合条件的账号后重新提交。

## 通过 API 接入自己的站点

不开发网站也可以开展业务，直接在后台生成并分发卡密即可。如果已经有自己的商城或自动发货系统，可以在控制台生成 API Token，通过合伙人管理 API 接管卡片、卡密、订单和账号检测；不想手写对接代码时，也可以把公开的 `llms.txt` 文档地址直接交给 AI Agent，让它自己读取认证方式、完整端点、参数、状态枚举和错误码。

**基础信息**

- 合伙人管理 API 基础地址：`https://ai.corouter.cc/api/v1/partner-api`
- 面向公众/终端用户的免鉴权地址：`https://ai.corouter.cc/api/v1/public`
- 面向 AI Agent 的公开接口文档：`https://ai.corouter.cc/llms.txt`（不含任何 Token，可放心分享，但 Agent 调用管理接口时仍需从自己的服务端密钥存储读取 Token）
- 所有合伙人管理请求都需要携带 `Authorization: Bearer <API_TOKEN>`；JSON 请求体需要 `Content-Type: application/json`
- 响应统一为 `{ "code": number, "data": any, "message": string, "request_id"?: string }`，`code = 0` 表示成功
- 分页参数为 `page`（默认 1）和 `limit`（默认 8，范围 1–100），返回 `data.items` 和 `data.pagination`
- 命中限速会返回 HTTP 429，应停止请求并按响应头 `Retry-After` 等待

**限速规则**（按客户端 IP，默认值，实际额度可由平台调整）：全部 API 600 次/分钟；登录 5 次/分钟；匿名卡密校验、提交与账号检测合计 10 次/分钟；匿名进度查询 120 次/分钟；认证合伙人 API 300 次/分钟。管理员可以把特定合伙人加入不限速白名单，但匿名接口仍按 IP 限速。

**主要接口分类**：

- 支付地区与套餐：`GET /payment-regions`、`GET /plan-offerings`；
- 卡片管理：`GET/POST /cards`、`GET /cards/:id`、`PATCH /cards/:id`（启用/暂停/归档）、`PATCH /cards/:id/pool`（调整所属卡池）、`POST /cards/:id/restore`；
- 卡密管理：`POST /card-keys`（生成，1–50 枚/次）、`GET /card-keys`、`GET /card-keys/:id`、`PATCH /card-keys/:id`（停用）、`POST /card-keys/:id/restore`、`POST /card-keys/replace`（批量销毁换新）；
- 充值记录：`GET /recharge-logs`（可按状态、完整订单号、完整卡密筛选）；
- 账号订阅检测：`POST /accounts/subscription/check`（合伙人版，需要 Token）以及 `POST /api/v1/public/accounts/subscription/check`（公开版，无需 Token）；
- 认证充值三步流程：
  1. `POST /recharge/card-keys/verify` — 校验本站点卡密，创建充值会话，返回 `recharge_session_id`、`access_token`、`session_url` 等；
  2. `POST /recharge/sessions/:session_id/submit` — 携带 `X-Recharge-Token` 和唯一的 `Idempotency-Key`（8–120 字符，网络重试必须复用原值）提交终端用户的 Session Payload，成功返回 HTTP 202 和 `order_no`；
  3. `GET /recharge/sessions/:session_id/status` — 携带 `X-Recharge-Token` 轮询进度，建议每 1–2 秒查询一次，直到状态变为 `succeeded`、`failed`、`already_active` 或 `canceled`；`progress_percent`（0–100）可直接用于绘制进度条。

接入时建议注意以下几点：

- API Token 与卡号、CVV、完整卡密、充值访问令牌、ChatGPT 认证信息一样属于敏感数据，只在服务端使用，不写入日志或持久化存储；
- 为提交充值的请求生成并保存业务幂等键，避免网络重试导致重复扣款；
- 常见业务错误码集中在 1xxx（参数/鉴权/限速类）、2xxx（卡片/卡密/充值/积分/账号资格类），可以据此在自己的系统里做针对性提示，例如 `2501` 表示可用积分不足，`2603`–`2606` 分别对应已有有效订阅、非 Personal 工作区、账单币种不兼容、非 Free 状态；
- 将平台订单状态同步到自己的订单系统，方便客户查询和售后；
- 正式上线前先用少量订单验证完整链路，包括卡密生成、卡片派单和账号检测拦截逻辑。

具体字段与完整示例请以合伙人控制台里的 API 文档页面或 `https://ai.corouter.cc/llms.txt` 为准。

## 积分消耗和预扣规则

不同套餐的代付成本不再统一，**Go、Plus 套餐每次代付消耗 10 积分，Pro 5x、Pro 20x 套餐每次代付消耗 20 积分**；该成本会在卡密生成时就固化保存，客户提交充值时按此数值预扣（`credit_reserved` 增加，`credit_balance` 暂不变）。预扣期间，这部分积分仍显示在账户余额中，但不会计入可用积分。平台目前**没有"人工复核"这个中间状态**——订单只会落在 `pending`（排队）、`processing`（执行中）、`succeeded`、`already_active`、`failed`、`canceled` 六种状态里，终态一旦写入就会在同一个事务里完成积分处理，不需要等待人工介入：

| 订单结果                              |    最终消耗 | 积分处理方式                                                     |
| -------------------------------------- | -----------: | ---------------------------------------------------------------- |
| 充值成功（`succeeded`）                | 10 或 20 积分 | 正式结算预扣积分，卡密标记已使用并永久绑定实际卡片                 |
| 目标套餐池与全套餐池暂时都忙（`pending`） |     暂不结算 | 不算失败，继续保留预扣，等待卡片租约释放后自动重新领取执行         |
| 两个卡池均无可用卡片（`failed`）        |       0 积分 | 完整释放预扣积分，卡密退回未使用、保持未绑定，补卡或调整卡池后可重新提交 |
| 账号已有目标套餐（`already_active`）    |       0 积分 | 完整释放预扣积分，卡密退回未使用，可更换符合条件的账号重新提交       |
| 付款前、可归因于卡片的失败（`failed`）  | 1 积分服务费 | 释放套餐预扣，另从余额扣除 1 积分失败服务费（例如绑卡被风控明确拒付） |
| 付款前、非卡片原因的失败（`failed`）    |       0 积分 | 完整释放预扣积分，不收取服务费（例如平台配置、网络、卡片池临时无容量） |
| 付款已提交但结果无法确认（`failed`）    | 10 或 20 积分 | 为避免重复扣款，按已消费处理：正式结算积分并永久绑定实际卡片         |
| Pro 前置 Plus 已成功、目标套餐升级失败（`failed`） | 10 或 20 积分 | 按已消费处理，正式结算并绑定卡片，账号转入后续续费处理流程           |

举个例子：账户余额为 50 积分，提交一笔 Go 套餐订单后，后台会显示余额 50、预扣 10、可用 40，成功后余额变为 40；如果是付款前非卡片原因导致的失败，余额恢复为 50；如果是付款前可归因于卡片的失败，最终余额为 49。若是一笔 Pro 20x 套餐订单，提交后余额 50、预扣 20、可用 30，成功后余额为 30，同类失败规则同样适用（非卡片原因完整释放，卡片原因失败只扣 1 积分服务费）。

这里所说的"付款前"和"付款已提交/结果无法确认"是系统内部按支付进度持续记录的边界，不需要合伙人自己判断：即使执行 Worker 中途崩溃，维护任务也会每分钟扫描卡片租约已过期但仍停在 `processing` 的订单，按已记录的支付进度自动补写终态——付款边界之前中断的会释放卡密和积分，边界之后中断的会按已消费处理，全程不产生需要人工复核的中间订单。支付卡上的实际扣款和平台积分消耗是两套独立记录，积分的每一次变化都会出现在合伙人的积分流水中。

## 异常订单如何被系统自动了结

平台**已经取消了人工复核环节**：无论卡片池暂时全忙、支付被拒、结果无法确认，还是执行 Worker 意外中断，订单最终都会由系统自动落入六种确定状态之一（`pending`、`processing`、`succeeded`、`already_active`、`failed`、`canceled`），不再存在需要合伙人或平台方手工判断"到底扣没扣款"的中间订单。合伙人可以在后台的"充值记录"里按订单号、卡密或账号随时查看当前状态和失败原因。

具体判定逻辑：

- **卡片池暂时全忙**：订单停在 `pending` 排队，不算失败，等某张匹配卡片的租约释放后会被自动重新领取执行，不会因为等待而额外占用积分或阻塞其他套餐/其他合伙人的订单；
- **卡片池确实没有可用卡片**（不在冷却、未过期、未归档的卡片一张都没有）：直接判定 `failed`，释放预扣积分，卡密退回未使用，补充或恢复匹配卡池的卡片后可以重新提交；
- **付款已经提交、或前置付款已经完成，但结果无法确认**：为了避免同一账号被重复扣款，系统会按"已消费"处理——正式结算积分、把卡密永久绑定到实际使用的卡片，不会再次发起支付；
- **执行 Worker 中途崩溃**：维护任务每分钟会扫描卡片租约已经过期但订单仍停在 `processing` 的记录，依据系统内部持续记录的支付进度自动补写终态，同样遵循"付款前释放、付款边界后消费"的规则，不需要人工介入。

因此遇到状态还没有变化的订单，不需要联系人工"申请复核"，也不要因为暂时没有结果就重新生成卡密或让客户重复提交——按上面的规则耐心等待终态即可；如果长时间停留在 `pending`/`processing` 没有变化，再携带订单号联系平台负责人排查。

Go 和 Plus 每次消耗 10 积分；Pro 5x 和 Pro 20x 每次消耗 20 积分。成本随卡密保存，并在使用者提交充值时预扣。

### 卡密池和卡片池有什么区别？

卡密池保存按地区和套餐生成、可供分发的一次性凭证；卡片池保存真正用于付款的银行卡。具体卡片会在订单开始执行时按套餐卡池规则领取，卡密生成阶段不占用任何卡片的绑卡暴露次数。

### 卡密在什么时候绑定卡片？

卡密生成后进入独立卡密池，处于"未绑定"状态。订单开始执行时才领取具体卡片，订单成功或付款进入不可逆结果后才形成永久绑定。

### 专属卡池和全套餐卡池应该怎么选？

确定用于某个最终套餐的卡片放入对应专属卡池；需要为多种套餐提供公共后备时放入全套餐卡池。派单始终先查同套餐专属池，再查全套餐池。

### 一定要开发自己的网站吗？

不需要。最简单的方式是在控制台生成卡密后直接分发给客户；有自己的站点或自动发货系统时，可以使用合伙人 API，甚至直接把 `llms.txt` 文档地址交给 AI Agent 来完成接入。

### 客户需要注册平台账号吗？

不需要。客户拿到卡密后，可以直接进入公开充值页面完成卡密校验和充值；只是想确认账号订阅状态，也可以直接使用免费的订阅检测功能，同样不需要注册。

### 目标账号已有订阅时如何处理？

系统会在付款环节前停止提交，卡密恢复可用状态，套餐预扣积分完整释放。需要等当前订阅到期、订阅检测结果显示 Free 后，才能用该账号重新提交；也可以直接更换一个符合条件的账号。

### 关闭自动续费后可以立刻充值吗？

不可以。关闭自动续费只在下一个计费周期生效，当前周期内账号仍处于有效订阅状态，请等待检测结果显示 Free 后再提交。

### 支付结果暂时不能确认怎么办？

不会再进入人工复核。为避免同一账号被重复扣款，系统会把"结果无法确认"直接按已消费处理：正式结算积分，卡密永久绑定实际使用的卡片，订单状态写为 `failed`。如果确实是平台侧原因导致的失败（不可归因于卡片），则会完整释放预扣积分，卡密退回未使用。

### 现在还有人工复核吗？

没有了。平台已经把这个中间状态彻底移除，控制台、公开页面、API 和订单状态机里都不再有"待人工复核"的订单——所有订单要么在排队（`pending`），要么已经落入 `succeeded`/`already_active`/`failed`/`canceled` 之一的确定终态；哪怕代充 Worker 中途崩溃，维护任务也会按已记录的支付进度自动补写终态。
